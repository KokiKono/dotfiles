# データベースのスキーマと書き方

## プロパティ

| プロパティ | 型 | 埋め方 |
|---|---|---|
| `用語` | title | 会話に出てきた表記のまま。略語なら略語のまま（正式名称は「読み・別名」へ） |
| `読み・別名` | rich text | 正式名称、英略語の展開、表記ゆれ、社内での別の呼び方。カンマ区切り |
| `種別` | select | `社内用語` / `プロダクト・機能名` / `業界用語` / `技術用語` / `略語` |
| `ひとこと定義` | rich text | **1〜2 文**。一覧で読んで思い出せる長さに収める |
| `社内での使われ方` | rich text | この会社の文脈での使われ方。一般的な意味との差があればそこを書く |
| `初出コンテキスト` | select | `Slack` / `PR・コード` / `会議` / `ドキュメント` / `AIとの会話` |
| `出典URL` | url | 元の文脈（Slack パーマリンク、PR、Notion ページ）。無ければ空 |
| `公式定義` | url | 社内の既存用語集にエントリがあればその URL |
| `登録日` | date | 当日 |

`種別` の選び分け:

- `社内用語` — この会社でしか通じない。社内の制度・慣習・組織・ワークフローの呼び名
- `プロダクト・機能名` — 自社プロダクトやその機能・画面・内部コンポーネントの名前
- `業界用語` — 業界では通じるが、この業界に来て初めて出会った語
- `技術用語` — 一般的な技術語だが、この会社の文脈で特殊な意味を持つもの
- `略語` — 主に略語であることが引っかかりになる語（展開を「読み・別名」に必ず書く）

一般的な意味と社内の意味がずれている語は、`技術用語` や `業界用語` ではなく **`社内用語`** に寄せる。
「一般と違う」ことこそが記録する理由だから。

## 社内で意味が割れている語

同じ語が部署や文脈で別の意味で使われていることがある（開発側とビジネス側で指すものが違う、
英略語がたまたま同綴りで別義、など）。この場合も**レコードは 1 つにまとめる**。
別レコードにすると、次に出会ったときどちらを引けばいいか分からなくなる。

- `ひとこと定義` に主な用法を書き、「〜の文脈では別の意味」と一言添える
- `社内での使われ方` に用法ごとの違いを書く
- 本文の `## わかったこと` を `### 用法A（開発）` / `### 用法B（ビジネス）` に割る

**どちらの意味かを断定しない。** 複数の意味を見つけたこと自体が記録する価値のある発見で、
文脈からの推測は推測として `## まだわからないこと` に置く。

## ページ本文のテンプレ

プロパティは一覧で見る用、本文は**後から読み返して思い出す用**。

```markdown
## わかったこと

（自分の言葉での理解。2〜5 行。ユーザーが理解したときの言い回しを活かす）

## 元の文脈

> （Slack の発言 / PR の説明 / コードのコメントなど、引っかかった原文の引用）

## 公式定義との差分

（`公式定義` を埋めたときだけ置く節。自分の理解とどう違ったかを 1〜3 行）

## まだわからないこと

（会話で解消しなかった疑問。無ければこの節ごと省く）
```

節は**中身があるものだけ置く**。空の見出しを並べない。

## 更新するとき

既存ページに追記する場合は、上のテンプレを作り直さず本文の末尾に足す:

```markdown
## 追記（2026-10-08）

（新しく分かったこと。前に書いたことが間違っていたなら、消さずに「訂正」として書く）
```

**前の記述を消さない。** 理解が変わっていく過程そのものが、この用語帳の中身になる。
