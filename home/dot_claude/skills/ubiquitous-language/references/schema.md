# データベースのスキーマと書き方

追記先はユビキタス言語専用の DB ではなく、**イシュー検討メモと同居する個人メモ DB**。
`種別` で行を見分けるので、読むときも書くときも必ず `種別 = ユビキタス言語` で絞る。

## プロパティ

| プロパティ | 型 | 埋め方 |
|---|---|---|
| `名前` | title | 会話に出てきた表記のまま。略語なら略語のまま（正式名称は本文の「読み・別名」へ） |
| `種別` | select | 常に `ユビキタス言語`（もう一方の `イシュー検討メモ` はこのスキルでは触らない） |
| `Github Issue` | url | 出典が GitHub の issue / PR のときだけその URL。それ以外は空 |

用語の中身（定義・別名・使われ方・出典など）を入れる列は無い。**すべて本文の「概要」節に書く。**
一覧で見たい情報もここに置くので、概要の 1 段落目は一覧で読んで思い出せる長さにする。

## ページ本文のテンプレ

1. **DB テンプレートの記載ルール callout** — 設定の `template_url` のページを fetch し、
   本文の callout をそのまま先頭に写す。文面をスキル側に持たないのは、ルールの正本が
   Notion 側にあり、そちらで書き換えられるから。callout に書かれたルールにも従うこと
   （たとえば「他の用語と意味が重なるなら整理する」）
2. **`## 概要`** — 旧 DB で列だった項目
3. **`---`** の区切り
4. **`## わかったこと` 以降** — 後から読み返して思い出す用

```markdown
<（template_url の callout をそのまま）>
## 概要
（ひとこと定義。1〜2 文。一覧で読んで思い出せる長さ）
- 読み・別名: （正式名称、英略語の展開、表記ゆれ、社内での別の呼び方。カンマ区切り）
- 社内での使われ方: （この会社の文脈での使われ方。一般的な意味との差があればそこを書く）
- 分類: （下の 5 つから 1 つ） / 初出: （Slack / PR・コード / 会議 / ドキュメント / AIとの会話） / 登録日: YYYY-MM-DD
- 公式定義: （社内の既存用語集のエントリ。ページメンションで）
- 出典: （元の文脈。Notion ならページメンション、それ以外はリンク）
- 関連: （意味が近い・重なる既存の用語ページへのメンション）
---
## わかったこと

（自分の言葉での理解。2〜5 行。ユーザーが理解したときの言い回しを活かす）

## 元の文脈

> （Slack の発言 / PR の説明 / コードのコメントなど、引っかかった原文の引用）

## 公式定義との差分

（公式定義を見つけたときだけ置く節。自分の理解とどう違ったかを 1〜3 行）

## まだわからないこと

（会話で解消しなかった疑問。無ければこの節ごと省く）
```

節も概要の行も**中身があるものだけ置く**。空の見出しや `公式定義:` だけの行を並べない。
`<` は `\<` とエスケープする（`&lt;` と書くとそのまま文字として残る）。

`分類` の選び分け:

- `社内用語` — この会社でしか通じない。社内の制度・慣習・組織・ワークフローの呼び名
- `プロダクト・機能名` — 自社プロダクトやその機能・画面・内部コンポーネントの名前
- `業界用語` — 業界では通じるが、この業界に来て初めて出会った語
- `技術用語` — 一般的な技術語だが、この会社の文脈で特殊な意味を持つもの
- `略語` — 主に略語であることが引っかかりになる語（展開を「読み・別名」に必ず書く）

一般的な意味と社内の意味がずれている語は、`技術用語` や `業界用語` ではなく **`社内用語`** に寄せる。
「一般と違う」ことこそが記録する理由だから。

## 関連と重複の整理

記載ルールに「意味の重複は避けて整理する」とある。新しく書く語が既存の語と重なるときは:

- **同じものの別名** → 新規に作らず、既存ページの「読み・別名」に足して追記する（SKILL.md §2）
- **隣接する別概念**（片方がもう片方の部品、同じ処理の別段階など）→ 両方作ってよいが、
  `関連` で互いにメンションし、違いを `社内での使われ方` に一言書く。
  既存ページの `関連` 行にも新しいページを足す
- 既存ページの「まだわからないこと」に今回の語が答えているなら、その行の後ろに
  答えのページをメンションで添える

## 社内で意味が割れている語

同じ語が部署や文脈で別の意味で使われていることがある（開発側とビジネス側で指すものが違う、
英略語がたまたま同綴りで別義、など）。この場合も**ページは 1 つにまとめる**。
別ページにすると、次に出会ったときどちらを引けばいいか分からなくなる。

- 概要の 1 段落目に主な用法を書き、「〜の文脈では別の意味」と一言添える
- `社内での使われ方` に用法ごとの違いを書く
- 本文の `## わかったこと` を `### 用法A（開発）` / `### 用法B（ビジネス）` に割る

**どちらの意味かを断定しない。** 複数の意味を見つけたこと自体が記録する価値のある発見で、
文脈からの推測は推測として `## まだわからないこと` に置く。

## 更新するとき

既存ページに追記する場合は、上のテンプレを作り直さず本文の末尾に足す:

```markdown
## 追記（2026-10-08）

（新しく分かったこと。前に書いたことが間違っていたなら、消さずに「訂正」として書く）
```

概要の行は、空だった項目を足すのと「読み・別名」「関連」に追記するのはよいが、
既存の記述は書き換えない。

**前の記述を消さない。** 理解が変わっていく過程そのものが、この用語帳の中身になる。
