# 記録する / しないの線引き

確認を取らずに書き込む方針なので、**ここが雑だと用語帳が使い物にならなくなる**。
ノイズが増えた用語帳は見返されなくなり、見返されない用語帳は書く意味がない。
迷ったら書かない側に倒す。取りこぼしは「用語帳に追加して」の一言で後から拾えるが、
ノイズは自分で消しに行かないと消えない。

## 2 つとも満たすときだけ書く

### 条件 A: この会社の外では通じない、または意味がずれる

- 社内の制度・組織・ワークフロー・慣習の呼び名
- 自社プロダクトや、その機能・画面・内部コンポーネント・バッチの名前
- 社内でしか使われない略語
- 一般的な語だが、この会社では違う意味・狭い意味で使われている語
- 業界に入って初めて出会った業界用語

### 条件 B: ユーザーが今この会話で理解した

- 「○○って何？」と聞いて、こちらが説明した
- Slack・PR・ドキュメントを一緒に読んでいて、知らない固有名詞をこちらが解説した
- ユーザーが自分で調べた内容を口に出し、こちらが補足・訂正した

逆に、**ユーザーがすでに知っていて会話に出しただけの語は書かない**。

## 書かないもの

| 例 | 理由 |
|---|---|
| `useMemo` / `N+1` / `CORS` / `冪等性` | 一般的な技術語。著者は基本情報技術者・Web 10 年で、react / typescript / laravel / mysql は既知 |
| 一般的な SaaS・OSS の名前（よく知られたツール） | 公式ドキュメントを引けば済む。用語帳の仕事ではない |
| 人名・チャンネル名・リポジトリ名そのもの | 用語ではない。ただし**その名前が概念を指している**なら書く |
| 一度きりで二度と出てこなそうな固有名詞 | 思い出す必要がない |
| 会話に出ただけで、意味を掘り下げていない語 | 書くべき中身がない。推測で埋めることになる |
| ユーザーが説明した側の語 | 本人が既に理解している |

## 判断に迷う形

- **一般語に見えるが社内で意味が違う** → **書く。** むしろ最も価値が高い。
  「一般的には△△だが、ここでは○○を指す」が本文の主役になる
- **業界では常識だが本人は初見** → **書く。** 新しい業界に来た以上、これも社内用語と同じ扱いでよい
- **略語の展開を教えただけ** → 展開が分かれば意味も分かる程度なら**書かない**。
  展開しても何のことか分からない（社内文脈が要る）なら**書く**
- **ユーザーが「知ってる」と言った** → **書かない。** 本人の申告を疑わない

## 判断の記録は残さない

記録しないと決めたとき、その判断を会話に出さない。黙って本題に戻る。
記録したときも報告は 1 行だけ。**用語帳はユーザーの作業を止めない範囲で動くもの**で、
これ自体が話題になると本末転倒になる。
