# hello-search

社内の情報は Slack・Notion・GitHub・kb に散らばっていて、1 か所だけ見ても全体が分からない。
このスキルは**同じ問いを全部の置き場に投げ、読んだ中身を出典付きで 1 つにまとめる**。
まとめた結果を後で読み返したいときは、Notion のメモ DB に登録する。

各ソースの検索のコツは `references/sources.md`、登録するページの形は `references/notion-memo.md` にある。
検索を始める前に `sources.md` を、登録する前に `notion-memo.md` を読む。

## 0. 設定を読む

```bash
cat ~/.claude/hello-search.local.json
```

| キー | 意味 |
|---|---|
| `database_url` | 登録先の Notion データベース（個人メモ DB） |
| `data_source_url` | その data source（`collection://…`）。`notion-create-pages` の親と `notion-query-data-sources` に渡す |
| `template_url` | `種別 = イシュー検討メモ` の DB テンプレート。本文先頭の記載ルール callout をここから写す |
| `github_owner` | `gh search` の `--owner` に渡す org |
| `slack_channel_hints` | 最初に当たるチャンネル名の配列（空でよい） |
| `kb_path` | kb の作業ツリー（既定 `~/git_clone/local/kb`） |
| `dry_run` | `true` なら Notion に書かず、書く内容を表示するだけ |

**このファイルは追跡外**（スキル本体は public リポジトリにある）。
無い / `data_source_url` が空なら `setup` モードへ。引数が `setup` のときも同じ。

## 1. 問いを分解する

検索を投げる前に、次の 3 つを短く決める（ユーザーには見せなくてよい）。

- **知りたいこと**: 経緯なのか、現在の仕様なのか、担当者なのか、未決の論点なのか。
  これで読むべき資料が変わる（経緯なら Slack と issue、現仕様なら Notion とコード）
- **検索語**: 日本語・英語・略語・コード上の識別子を 3〜6 個。社内用語は表記ゆれが多いので、
  メモ DB の `種別 = ユビキタス言語` の `読み・別名` に載っていれば、その別名も足す
- **期間**: 「最近の」「リリース前の」などの手がかりがあれば日付で絞る

issue の URL を渡されたら、まず `gh issue view <url> --comments` で本文を読み、そこから検索語を取る。
issue 本文にリンクされた Slack / Notion は検索より先に直接開く。

## 2. 横断で検索する

Slack・Notion・GitHub・kb の検索は互いに依存しないので、**1 回の応答でまとめて呼ぶ**。
各ソースで上位を見て、関係ありそうなものだけ中身まで読む（スレッド全体、ページ本文、issue のコメント）。
検索結果の抜粋だけで結論を書かない。抜粋は前後の文脈が欠けていて、決定が後で覆っていることがよくある。

1 巡目で見つかった語（チャンネル名、ページ名、担当者、別名）で 2 巡目を投げてよい。
**3 巡目は投げない。** それでも見つからなければ、見つからなかったことを報告する。

コードの実装を確かめる必要があるときは、カレントがその業務リポジトリなら codebase-memory を使う。

## 3. まとめる

```markdown
## <調べたこと>

**結論**: 2〜3 文。分かったことと、分からなかったこと

### 分かったこと
- <事実>（[出典名](URL), YYYY-MM-DD）

### 食い違い・未確定
- <A では X、B では Y。新しいのは B>（両方のリンク）

### 次に当たる先
- <誰に聞くか / どこを見るか>（見つからなかったときだけ）
```

- **事実には必ずリンクと日付を付ける。** 日付が無いと、古い決定と新しい決定を読み手が区別できない
- ソース同士で食い違ったら、どちらかを黙って採らず両方を並べ、新しい方を明記する
- 推測は「推測」と書いて事実と分ける
- 結果が少ないときは、どの検索語でどこを探したかを 1 行で添える（探していない場所と区別するため）

## 4. 登録するか決める

| 場面 | 動き |
|---|---|
| ユーザーが「残して」「メモして」「登録して」と言った / 引数に `--save` | 登録する |
| GitHub issue を起点にした調査で、結論が出た | 確認せずに登録する（同じ issue のページがあれば追記） |
| それ以外 | 登録せず、最後に「メモ DB に残しますか？」と 1 行だけ添える |

登録の手順は `references/notion-memo.md`。`dry_run` が `true` なら書く内容を表示して終える。

登録したら 1 行だけ報告する。

```
📝 メモ DB に「#123 ○○」を登録（リンク）
```

調べる途中で知らなかった社内用語を説明した場合は、ubiquitous-language スキルの判断に任せる
（このスキルでは用語のページを作らない）。

## setup モード

1. 登録先の DB の URL を聞く。ubiquitous-language と同じ個人メモ DB を使うのが基本なので、
   `~/.claude/ubiquitous-language.local.json` があれば `database_url` / `data_source_url` を流用してよいか聞く
2. DB を fetch し、`collection://…` と、`種別 = イシュー検討メモ` の DB テンプレートの URL を取る
3. `github_owner` は `~/.pzshrc` の `HELLO_RUN_ISSUE_REPO`（`<org>/<repo>`）の org 部分から取れる:
   `zsh -c 'source ~/.pzshrc; print ${HELLO_RUN_ISSUE_REPO%%/*}'`
4. `~/.claude/hello-search.local.json` に書く。`dry_run` は最初 `true` にし、数回ためしてから `false` にするよう勧める

## 守ること

- **読んでいないものを要約しない。** 検索結果のタイトルや抜粋から中身を推し量って書かない
- **検索だけで終わらせない。** リンクの一覧を渡すのではなく、読んだうえで問いに答える
- **Slack・GitHub には書き込まない。** 投稿・リアクション・issue コメントはこのスキルの範囲外
- **社内の固有名詞をこのスキルのファイルに書かない。** 例が要るときは `○○` / `△△` にする。
  `references/` も含めて public リポジトリに入っている
