# 定義ファイルと結果の書式

## 定義（mutations.json）

```json
{
  "runner": "rspec",
  "command": ["bin/rspec", "--fail-fast"],
  "tests": {
    "app/services/○○_service.rb": ["spec/services/○○_service_spec.rb"],
    "*": ["spec/requests/○○_spec.rb"]
  },
  "timeout": 300,
  "mutations": [
    {
      "label": "票/しきい値: 再訪 4 回 → 5 回",
      "file": "app/services/○○_service.rb",
      "old": "THRESHOLD = 4",
      "new": "THRESHOLD = 5",
      "breaks": "再訪が 4 回の人に満点の票を付ける"
    }
  ]
}
```

| キー | 必須 | 中身 |
|---|---|---|
| `command` | ○ | テストを流すコマンド（文字列の配列。シェルは通さない）。`tests` を書くときは、テストのファイルを入れない |
| `tests` | △ | 変異ごとに流すテストのファイル。`command` の後ろに足して流す。変異する `file` をキーにした配列で書き、キーに無いファイルの変異には `"*"` の配列を流す。全部の変異に同じものを流すなら配列だけでよい。**これがあるときだけ結果をキャッシュする** |
| `runner` | △ | `rspec` / `jest` / `vitest`。集計の行の見分け方を決める。他の道具なら `summary_pattern` を書く |
| `summary_pattern` | △ | テストが実行されたときに必ず出る集計の行の正規表現。`runner` より優先する |
| `broken_pattern` | | 読み込みに失敗したファイルがあることを示す行の正規表現。`runner` より優先する |
| `timeout` | | 1 回の上限（秒）。省くと、変異を入れない 1 回にかかった時間の 3 倍（最低 30 秒）になる |
| `mutations[].label` | ○ | `<領域>/<観点>: <何をどう変えるか>`。重複させない。接頭辞で `--only` に使う |
| `mutations[].file` | ○ | 作業ツリーのルートからの相対パス |
| `mutations[].old` | ○ | 書き換え前の文字列。**ファイルの中にちょうど 1 回だけ現れる**ようにする（`offset` があるときは、その位置にある文字列） |
| `mutations[].offset` | | ファイルの先頭からのバイト位置。あると、その位置が `old` で始まるときだけ書き換える。`gen_mutations.py` が付ける。手では書かない |
| `mutations[].new` | ○ | 書き換え後の文字列。行ごと消すなら `old` に改行まで含めて `""` にする |
| `mutations[].breaks` | | この変異が壊す仕様（振る舞い）。スクリプトは使わない。生き残りを分類するときの手がかりにする |

- `old` が 2 回以上現れるときは、前後の文字を足して 1 回にする。0 回なら定義が古い
- `offset` を持つ変異は、コードを直すと位置がずれて `invalid` になる。候補を作り直す
- 同じ `old` に別の `new` を当てる変異を並べてよい（1 つずつ入れて戻すので、ぶつからない）
- `--fail-fast`（RSpec）や `--bail`（Jest / Vitest）を付けると、検出できる変異が早く終わる
- `tests` にはその実装を確かめているテストだけを書く。関係の薄いテストまで入れると、そのテストを
  直すたびにキャッシュが外れる。`tests` のファイルが無いとき、`"*"` が無くてキーにも無い `file` があるときは、流す前に止まる
- `tests` に書けるのは実在するファイルだけで、`command` の末尾に足して流す。行番号つきの指定やディレクトリ、
  末尾に引数を足せない `command`（`sh -c "…"` など）では使えない。そのときは今までどおり `command` に
  テストを書く（キャッシュは使われない）

## キャッシュ

`run_mutations.py` は、`tests` のある定義の結果を `~/.cache/mutation-check/cache.sqlite3`（SQLite）に
記録し、次からは同じ変異を流さずに返す。kb には置かない（消えても流し直せば戻るので、履歴に残す意味が無い）。
持つのはハッシュと結果だけで、ソースやテストの中身は持たない。

| 何が同じなら前の結果を返すか | 中身 |
|---|---|
| ソースの側 | `command`、集計の行の見分け方、`file` のパス、変異を入れた後のファイルの中身、同じテストを 1 つでも共有している他の変異対象のファイルの中身。label と位置は見ないので、名前を変えても、別の PR やブランチでも当たる |
| テストの側 | その変異の `tests` のファイルの中身 |

- テストの側が変わっていても、行やファイルを足しただけなら `killed` は返す（落ちていたテストは落ちたままなので）。
  `survived` は足したテストで検出に変わりうるので流し直す。行を消した・書き換えたときは `killed` も流し直す
- 記録するのは `killed` と `survived` だけ。`broken`・`timeout`・`invalid` は毎回流す
- 変異を入れない 1 回（基準）は、変異を流し始める前にテストの組ごとに流す。省くのは、その組の変異が全部、
  テストが記録したときと同じ中身でキャッシュから返るときだけ。テストを足した後は、`killed` を使い回す
  ときも基準を流し、足したテストが変異を入れていないコードで通ることを確かめる
- ファイルを 1 行でも直すと、そのファイルの変異と、同じテストを共有している他のファイルの変異を全部流し直す
  （同じ PR で直した呼び出し先の変更を拾うため）。テストを共有していないファイルの変異はキャッシュから返る
- 流している間にテストや他の変異対象のファイルが変わったら、その結果は記録しない
- 定義に出てこないファイル（PR で変えていない呼び出し先、factory、共通の前処理、Gemfile.lock）を
  変えても気づかない。別のブランチや worktree で記録した結果も、それらが違っていても返る
- テストに足した行が既存のテストを弱めた場合（前処理に足した、`skip` を足した、囲んで無効にした）も、
  `killed` を返してしまう
- 環境の不調（DB に繋がらない等）で example が落ちた結果も `killed` として残る
- 上のどれかに心当たりがあるときは `--no-cache` を付ける
- キャッシュの読み書きに失敗したら（ディスクが一杯、ロックが取れない）、以降はキャッシュを使わずに流す

| 引数・環境変数 | 働き |
|---|---|
| `--no-cache` | キャッシュを引かずに全部流す（結果は記録する） |
| `--clear-cache` | キャッシュを消して終わる（定義は要らない） |
| `MUTATION_CHECK_CACHE` | キャッシュの置き場を差し替える |

30 日使わなかった結果は、実行の終わりに消す。

### runner ごとの見分け方

| runner | 集計の行 | 読み込みの失敗 |
|---|---|---|
| `rspec` | `N examples, M failures` | `error(s) occurred outside of examples` |
| `jest` | `Tests: ... N total` | `Test suite failed to run` |
| `vitest` | `Tests  ... (N)` | `Failed Suites N` |

## 機械的な候補（gen_mutations.py）

差分で足した・変えた行に、決まった書き換えを当てる。1 か所の書き換えが 1 つの変異になり、label は
`auto/<種類>: <ファイル>:<行>:<桁> <元> → <書き換え後>`。

### Ruby（構文木から作る）

Prism（Ruby 3.3 以上に同梱のパーサ）で構文木にし、ノードの種類ごとに書き換える。文字列・ヒアドキュメント・
コメントの中は拾わない。書き換えた結果が構文エラーになる変異は出さない。

| 種類 | 書き換え |
|---|---|
| 比較 | `>=` → `>`、`<=` → `<`、`>` → `>=`、`<` → `<=`、`==` ↔ `!=` |
| 算術 | `+` ↔ `-`、`*` ↔ `/` |
| 論理 | `&&` ↔ `\|\|`、`and` ↔ `or` |
| 論理（左だけ）/（右だけ） | `a && b` を `a` だけ、`b` だけにする（`\|\|` も同じ） |
| 否定 | `!x` → `x` |
| 条件 | `if` ↔ `unless`（三項演算子と `elsif` は除く） |
| 条件を true に / false に | `if`・`unless`・三項演算子の条件式を丸ごと `true` / `false` にする |
| 真偽 | `true` ↔ `false` |
| 数値 | 整数 n → n + 1。1 は 0 にもする |
| メソッド | `present?` ↔ `blank?`、`any?` ↔ `none?`、`all?` → `any?`、`empty?` → `any?`、`min` ↔ `max`、`min_by` ↔ `max_by`、`first` ↔ `last`、`floor` ↔ `ceil`、`select` ↔ `reject`、`filter` → `reject` |
| 呼び出しの削除 | `.uniq` / `.compact` / `.distinct` を外してレシーバーだけにする |
| nil の扱い | `&.` → `.` |
| 文の削除 | 2 文以上が並ぶ所で、文を 1 つ消す。代入、定数・メソッド・クラスの定義は消さない（後ろの参照が NameError になり、どのテストでも落ちるだけなので） |

Prism を読める `ruby` が PATH に無いときと `--no-ast` を付けたときは、下の正規表現の作り方に落ちる
（標準エラーにその旨が出る。作り方で候補が変わるので、過去の結果と比べるときは注意する）。
対象のリポジトリのルートで実行すれば、そのリポジトリの Ruby が使われる。

### JS / TS（行の文字列に正規表現を当てる）

構文木は見ない。

| 種類 | 書き換え |
|---|---|
| 比較 | `>=` → `>`、`<=` → `<`、`>` → `>=`、`<` → `<=`、`==` ↔ `!=`、`===` ↔ `!==` |
| 論理 | `&&` ↔ `\|\|` |
| 真偽 | `true` ↔ `false` |
| 数値 | 整数 n → n + 1 |
| 算術 | `+` ↔ `-`、`*` ↔ `/`（前後に空白のあるもの） |
| 否定 | `!` を消す |
| 行の削除 | 早期に抜ける行（`if (…) return …;`）を消す |
| 取り出し | `.some(` ↔ `.every(`、`Math.min` ↔ `Math.max`、`Math.floor` ↔ `Math.ceil` |

- `<` と `>` は前後に空白のあるものだけを拾う。総称型や JSX のタグと区別するため
- 複数行にまたがる文字列やコメントの中は見分けられない。そこから出た変異は `broken` か生き残りになるので、定義から外す

## 結果（result.json）

```json
{
  "counts": { "killed": 34, "survived": 6, "broken": 3, "timeout": 0, "invalid": 0 },
  "results": [
    { "label": "…", "file": "…", "status": "survived", "summary": "12 examples, 0 failures", "seconds": 6.8 },
    { "label": "…", "file": "…", "status": "killed", "summary": "12 examples, 1 failure", "seconds": 0.0, "cached": true }
  ],
  "cached": 1
}
```

`cached` はキャッシュから返した件数で、`tests` のある定義のときだけ出る。キャッシュから返した結果には
`"cached": true` が付き、`summary` は記録したときのもの。

| status | 意味 | 次にやること |
|---|---|---|
| `killed` | テストが落ちた。その変異を検出できる | 何もしない |
| `survived` | テストが通った（生き残り） | テストの穴か、結果が変わらない書き換えかに分ける |
| `broken` | テストが実行されずに落ちた（構文が壊れた、読み込みで落ちた） | 変異を書き直す。検出には数えない |
| `timeout` | 上限を超えた（変異で無限ループになった等） | 変異を見直すか、上限を上げる |
| `invalid` | 定義の誤り（`old` が 0 回か 2 回以上、ファイルが無い） | 定義を直す |

検出率は `killed / (killed + survived)` で出す。`broken` を検出に数えると、テストが実際より強く見える。

## report.md

会話の報告と `report.md` は、この PR も mutation-check も知らない人が読む。次の決まりで書く。

- `killed`・`survived`・「検出」「生き残り」「変異」をそのまま使わない。次の言葉に置き換える

  | スクリプトの言葉 | 報告での言葉 |
  |---|---|
  | 変異 | わざと入れたバグ |
  | `killed`（検出） | テストが落ちて、バグに気づけた |
  | `survived`（生き残り） | テストが通ってしまい、バグを見逃した |
  | 生き残りが検出に変わった | テストを足した後は、同じバグを入れるとテストが落ちるようになった |
  | 結果が変わらない書き換え | 入れても動きが変わらず、テストでは見分けられない書き換え |

- 冒頭に、何を・なぜ・いつ・どこを・誰が・どうやって確かめたかを表で置く。結果はその後に書く
- 件数には、何のうちの何件かを添える（「80 / 114」だけで済ませない）
- 見逃したバグは 1 件ずつ表に書き、対応を次の 3 つのどれかに決める。まとめて 1 行にしない。
  表では絵文字を先頭に付け、対応していない行を目で拾えるようにする（会話の報告でも同じ）

  | 対応 | いつ使うか | 理由に書くこと |
  |---|---|---|
  | ✅ 対応した | テストを足し、流し直して、同じバグでテストが落ちることを確かめた | 足したテストのファイルと、足した例 |
  | ➖ 対応しなかった | 対応は要らない、または今回はしないと決めた（入れても動きが変わらない、使われていないコード、頼まれていない、PR の範囲外） | そう決めた理由。穴が残るなら、残ることも書く |
  | ⚠️ 対応できなかった | 対応が要るのに、できていない（テストを足してもまだ通る、実装を変えないとテストから見分けられない、テストの環境で再現できない） | 試したことと、できなかった理由、残っているリスク |

  「対応しなかった」と「対応できなかった」は、読む人が次に動くかどうかを分ける。穴が残っていて、
  対応する意思があったのにできていないものを「対応しなかった」に入れない

```markdown
# <repo>#<PR番号> の mutation-check

## 何を確かめたか

| | |
|---|---|
| 何を | <対象の処理を 1〜2 文で>。そのテストが、実装のバグに気づけるかを確かめた |
| なぜ | <流した理由。例: 判定の条件が多く、テストが通っていても結果を確かめていない行が残りうる> |
| いつ | YYYY-MM-DD |
| どこを | 実装: `<変異を入れたファイル>` / テスト: `<流したテストのファイル>` |
| 誰が | バグの候補は、スクリプトが決まった書き換えで N 件、テストを読んでいない別の AI が仕様から M 件作った。テストはこのセッションの AI が足した |
| どうやって | 実装にわざと小さなバグを 1 件ずつ入れ、そのたびにテストを流した。テストが落ちれば「気づけた」、通れば「見逃した」と数える |

## 結果

- 入れたバグ 40 件のうち、最初のテストで気づけたのは 34 件、見逃したのは 6 件
- 見逃した 6 件の対応: ✅ 対応した 5 件 / ➖ 対応しなかった 1 件 / ⚠️ 対応できなかった 0 件（1 件ずつの理由は下の表）
- 実装は変えていない
- <数えなかったもの。例: 3 件は構文が壊れてテストが実行されなかったので、どちらにも数えていない>

| 回 | commit | 前の回からしたこと | 入れたバグ | 気づけた | 見逃した | 実際に流した件数 |
|---|---|---|---|---|---|---|
| 1 | abc1234 | | 40 | 34 | 6 | 40 |
| 2 | def5678 | テストを足した | 40 | 39 | 1 | 6（残りの 34 件は前の回の結果を使った） |

## 見逃したバグと対応（6 件）

| 対応 | 件数 | 意味 |
|---|---|---|
| ✅ 対応した | 5 | テストを足し、同じバグを入れるとテストが落ちることを確かめた |
| ➖ 対応しなかった | 1 | 対応は要らない、または今回はしないと決めた。リスクは残っていないか、承知のうえで残している |
| ⚠️ 対応できなかった | 0 | 対応が要るのに、できていない。テストの穴が残っている |

| # | 場所 | 入れたバグ | テストが通ってしまった理由 | 対応 | 対応の内容、または対応していない理由 |
|---|---|---|---|---|---|
| 1 | `app/…/foo.rb:12` | 合計の比較を `>=` から `>` にする | 合計がしきい値ちょうどの例が無い | ✅ 対応した | `spec/…/foo_spec.rb` に、合計がしきい値ちょうどの例を足した |
| 2 | `app/…/foo.rb:30` | 空のときの早期 return を消す | 空の配列で保存を呼んでも何も起きない | ➖ 対応しなかった | 入れても動きが変わらず、テストでは見分けられない |
```

表の commit は、その回に流したコードのもの。pr-followup と「1-3. 2 回目以降」が、最後の行の commit を読む。
