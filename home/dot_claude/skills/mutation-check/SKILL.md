# mutation-check

カバレッジは「その行が実行されたか」しか見ない。実行されていても、結果を確かめていなければバグは通る。
このスキルは差分に変異（わざと入れる小さなバグ）を 1 つずつ入れてテストを流し、テストが落ちるかを見る。

- テストが落ちた変異は、その種類のバグを検出できる
- テストが通った変異（生き残り）は、次のどちらか
  - テストの穴: テストを足して塞ぐ
  - 結果が変わらない書き換え（例: 早期 return を消す、空の配列で保存を呼ぶ）: テストでは区別できないので残す

**生き残りを 0 にすることは目標にしない。** 生き残りを 1 件ずつ、穴か結果が変わらないかに分けるために使う。

## 流すタイミング

時間がかかり（数十通りで数分）、定義もコードを直すと古くなるので、毎コミットには流さない。

- 実装とテストが揃い、PR を Ready for review にする前に 1 回。PR を作ると pr-followup スキルが、
  AI レビューを始める前にこのスキルを 1 回呼ぶ
- 計算や判定の決まりが多い差分のときだけ（サービス・モデル・バッチの条件分岐、しきい値、集計）
- 画面の文言や設定だけの変更、テストがまだ揃っていない作業中の差分では流さない。そう伝えて終える

## 0. 対象と置き場を決める

1. 対象の差分を決める。引数の PR があれば `gh pr diff <番号>`、無ければ今のブランチの
   `git diff $(git merge-base origin/<既定ブランチ> HEAD)`
2. 作業ツリーが汚れていないことを確かめる（`git status --short`）。スクリプトはファイルを書き換えて戻すので、
   対象のファイルに未コミットの変更があれば、先にコミットするかユーザーに聞く
3. 定義と結果の置き場を作る。**定義は kb に置く**（リポジトリには入れない）

   ```bash
   DIR=$(~/.claude/skills/mutation-check/scripts/kb.sh <repo>-<PR番号>)   # PR が無ければ <repo>-<ブランチ名の / を - にしたもの>
   ```

   kb が無くて失敗したら、セッションの一時ディレクトリに置き、kb に残せなかったことを報告に書く
4. 同じリポジトリの過去の `report.md`（`$DIR/../<repo>-*/report.md`）があれば読む。穴を見つけた変異の種類は、今回も先に試す
5. 引数に `rerun` があるか、`$DIR/mutations.json` が既にあれば、定義を作り直さず 2 から始める。
   機械的な候補は位置で場所を決めるので、コードを直すと `invalid` になる。多ければ 1 からやり直す

## 1. 変異を作る

変異は 2 通りの作り方を合わせる。どちらも差分で**変更した行だけ**を対象にする。

| 作り方 | 得意なこと | 苦手なこと |
|---|---|---|
| 機械的（`gen_mutations.py`） | 演算子・条件式・真偽・数値・よく使うメソッド・文の削除を、決まった書き換えで漏れなく作る。選ぶ人の思い込みが入らない | 仕様は知らないので、仕様に踏み込んだ書き換えは作れない |
| subagent が考える | 仕様を壊す書き換え（集計の取り違え、タイムゾーン、保存するカラムの漏れ） | 思いついたものしか入らない |

### 1-1. 機械的な候補を出す

```bash
~/.claude/skills/mutation-check/scripts/gen_mutations.py \
  --base "$(git merge-base origin/<既定ブランチ> HEAD)" --out "$DIR/candidates.json"
```

対象は Ruby と JS / TS で、テストのファイル・文字列の中・コメントは飛ばす。Ruby は構文木（Prism）から作り、
JS / TS は行の文字列に正規表現を当てる。書き換えの一覧は [references/definition.md](references/definition.md) にある。

- 対象のリポジトリのルートで実行する（そのリポジトリの Ruby で構文木を作るため）
- 出力の件数が 100 を大きく超えるときは、流す時間（1 件あたりテスト 1 回）を見積もってユーザーに伝え、
  パスの引数で対象のファイルを絞るかを聞く

### 1-2. subagent に定義を作らせる

**変異の定義はこのセッションで書かず、subagent（Agent ツール、general-purpose）に作らせる。**
実装とテストを書いたセッションは、自分のテストが拾える書き換えばかりを思いつく。
subagent には差分と仕様だけを渡し、**テストのコードは読ませない**。

subagent には次を渡す。

- 差分の取り方（PR 番号か、`git diff <merge-base>`）と、作業ツリーのパス
- 仕様の出どころ（issue の URL、PR 本文、kb の README）。会話で決めた仕様は文章にして渡す
- `$DIR/candidates.json` と、書式の `~/.claude/skills/mutation-check/references/definition.md` のパス
- 過去の `report.md` で穴を見つけた変異の種類（0 の 4 で読んだもの）
- テストを流すコマンド（`runner` / `command` / `timeout`）。これはこのセッションで決める。
  差分に関係するテストのファイルだけを流すものにし、リポジトリの流し方（ラッパーのスクリプトなど）は
  その CLAUDE.md や package.json に従う

subagent には次を頼む。

1. `candidates.json` の変異を、**そのまま全部**定義に入れる。外してよいのはログの文言や型の注釈など
   振る舞いに関係しない行のものだけで、外したものは理由と一緒に返す。「テストが拾えそうにない」
   「結果が変わらなそう」では外さない（それを確かめるのがこのスキル）
2. 機械的な表に無い、仕様を壊す変異を足す。観点は次のとおり
   - 処理の削除（絞り込み、重複の除去、保存、削除）
   - nil・空・未設定の扱い
   - 日付とタイムゾーン、丸め（四捨五入と切り捨て）
   - 集計の取り違え（全体と内訳、件数と合計）
   - 更新の漏れ（保存するカラムを 1 つ落とす）、対象の取り違え（別の id、別の状態）
3. 足す変異には、壊す仕様（振る舞い）を `breaks` に書く。書けない変異は仕様に関係しないので入れない
4. 構文を壊さない。機械的な候補と同じ書き換えを言い換えて水増ししない
5. `$DIR/mutations.json` に書き、件数（機械的 / 足したもの / 外したもの）を返す。テストは流さない

## 2. 流す

作業ツリーのルートで実行する。数分かかるので Bash の `run_in_background` で流す。

```bash
~/.claude/skills/mutation-check/scripts/run_mutations.py "$DIR/mutations.json" --out "$DIR/result.json"
```

- 変異を入れる前のテストが落ちていれば、スクリプトは止まる。先にテストを直す
- `invalid`（`old` が 1 回だけ現れない等）と `broken`（構文が壊れた、読み込みで落ちた）は定義を直し、
  `--only <label の接頭辞>` でその分だけ流し直す
- 終わったら `git status --short` で、書き換えが残っていないことを確かめる

## 3. 生き残りを分ける

`survived` の変異を 1 件ずつ、実装とテストを読んで分ける。

- テストの穴: 変異で振る舞いが変わるのに、どのテストもその違いを見ていない。
  「どの入力なら結果が変わるか」を具体的に言えるなら穴
- 結果が変わらない書き換え: どんな入力でも外から見える結果が同じ。その理由を書く

それぞれに理由を付ける。行は実行されているのにテストが通る場合は、既存のテストがなぜ区別できないか
（データの組み方、確かめている値）まで書く。

## 4. 報告し、穴を塞ぐ

1. 次を報告する
   - 検出の数（`killed / (killed + survived)`。`broken`・`timeout` は別に数える）
   - テストの穴: 変異、通った理由、足すテストの案（どのファイルに、どんな入力と期待値で）
   - 結果が変わらない書き換え: 変異と理由
2. テストを足すのは、ユーザーに頼まれたときだけ。足したら次で、生き残りが検出に変わったことを確かめる

   ```bash
   ~/.claude/skills/mutation-check/scripts/run_mutations.py "$DIR/mutations.json" \
     --survivors-of "$DIR/result.json" --out "$DIR/result-2.json"
   ```

   まだ通る変異はテストの組み方を見直す。実装は変えない
3. `$DIR/report.md` に、回ごとの検出の数と、3 の分類を残す（書式は references/definition.md）

## 制約（報告に添える）

- 機械的な候補は決まった書き換えしか作らない（JS / TS は構文木も見ない）。一覧に無い書き換えと、
  subagent が挙げなかった書き換えに、テストが強いかどうかは分からない
- 検出の数はテストの強さの点数ではない。変異の選び方で変わるので、PR 同士で比べない

## やらないこと

- 生き残りを消すためだけに、実装を変えたり、結果が変わらない書き換えにテストを足したりする
- 変異を入れたままの commit・push（スクリプトが毎回戻す。途中で止めたときも `git status` で確かめる）
- 定義ファイルをリポジトリに置く
