# optimize-prompt

Claude（とくに Claude Code）に渡す**指示文**を、Anthropic のベストプラクティスに沿って診断し、改善版に書き直すスキル。

対象は、ユーザーが「Claude に読ませる文章」全般：スキルの `SKILL.md` 本文、サブエージェントのプロンプト、`CLAUDE.md`、スラッシュコマンドの定義、API で渡す system プロンプトやツール定義など。**「Claude に何をしてほしいか」を書いた文章**ならすべて対象になる。

## このスキルの狙い

プロンプト改善は「ルールに機械的に当てはめる」作業ではない。今のモデルは賢く、theory of mind を持つ。だから良いプロンプトとは、**やることを羅列した命令書ではなく、なぜそうしてほしいのかまで伝わる説明**になっている。診断でも書き直しでも、この観点を軸にすること。

特に見落とされがちで、かつ効果が大きいのが **過剰プロンプトの害**。旧世代向けに書かれた `CRITICAL:` / `You MUST` / `ALWAYS` / `NEVER` を多用した指示は、現行モデルでは**オーバートリガー**を起こす。「良くする」＝「足す」ではなく、**削って理由に置き換える**ことが改善になるケースが多い。

## ワークフロー

### 1. 対象プロンプトを受け取る

ユーザーが貼り付けたテキスト、あるいはファイルパス（`SKILL.md`、`CLAUDE.md` 等）を受け取る。ファイルパスなら Read してから診断する。何を Claude にさせる指示なのか、どのハーネス（Claude Code か API アプリか）で使うのかが曖昧なら、そこだけ短く確認する。

### 2. 診断する

`references/best-practices.md` のチェックリストに照らして、**該当する項目だけ**を挙げる。全項目を機械的に列挙しない。プロンプトごとに刺さる指摘は数個のはず。それぞれについて：

- **どの原則に反しているか**（例: 「やるな、ではなくやれ」「過剰プロンプト」）
- **具体的にどの箇所か**（原文を短く引用）
- **なぜ問題か**（そのモデル世代で実際に何が起きるか）

を簡潔に述べる。褒めるための水増しはしない。指摘がなければ「大きな問題はない」と正直に言う。

### 3. 改善版を書き直す

診断を反映した書き直し版を、**そのまま使える完成形**で提示する。書き直しの際は：

- **やらないこと、ではなくやることを書く。**「マークダウンを使うな」→「滑らかな散文の段落で書く」。
- **理由を添える。**「省略記号を使うな」→「読み上げエンジンが発音できないので省略記号は使わない」。理由があるとモデルは般化できる。
- **過剰な強調を落とす。**`CRITICAL:` `MUST` `ALWAYS` を、通常の指示文と「なぜ重要か」の説明に置き換える。本当にリスクの高い不可逆操作（削除・force push 等）にだけ強い確認ガードを残す。
- **構造が混在するなら XML タグで整理する。**指示・文脈・例・入力が混ざっているなら `<instructions>` `<context>` `<example>` 等で囲む。
- **例を足す価値があれば足す。**出力の形・トーンを固定したいなら few-shot 例を `<example>` タグで 1〜3 個。
- **ツールを使わせたいなら明示的に。**「変更を提案して」ではなく「この関数を変更して」。Claude Code 指示文でツールがアンダー/オーバートリガーしているなら、トリガー条件を「〜に役立つ場合に使う」の形に調整する。
- **元の意図と語り口は保つ。**改善は原文の目的を叶えるためのもの。勝手に機能や制約を足さない（オーバーエンジニアリングを避ける）。

書き直し版のあとに、**主要な変更点を 3〜5 個、before → after で**箇条書きにする。ユーザーが差分を追えるように。

## 出力テンプレート

```
## 診断
- **[原則名]**: 「<原文の引用>」— <なぜ問題か。そのモデルで何が起きるか>
- （該当する項目だけ。通常 2〜5 個）

## 改善版
<そのまま貼り付けて使える完成版プロンプト>

## 主な変更点
- <before> → <after>（<一言で理由>）
```

## 判断の指針

- **診断だけで書き直しを求められていない場合**でも、軽い書き直し案は添えると役立つことが多い。ただしユーザーが「診断だけ」と明言したら従う。
- **原文がすでに良い場合**は無理に指摘をひねり出さない。「ここは効いている」と認めた上で、あれば小さな磨き込みだけ提案する。
- **長いプロンプト（CLAUDE.md 全体など）**は、全文を書き直すと差分が追えなくなる。問題の大きいセクションに絞って before/after を示すか、ユーザーに範囲を確認する。
- モデル世代ごとの挙動差（オーバートリガー傾向、adaptive thinking、`think` という語への感度など）は `references/best-practices.md` の付録に、確認日付きで整理してある。版依存の指摘をするときは、その日付が古くなっていないか見る。対象モデルで再現を確かめていない癖を欠陥として指摘すると、直す必要のない箇所を直させることになる。

チェックリストの全項目と各原則の詳細・サンプル文言は `references/best-practices.md` にある。診断の観点を広げたいときや、書き直しに使える定型プロンプト片が欲しいときに読む。
