# comment-check

コメントを書いたセッションは issue も仕様も会話も知っているので、`# issue-12345（○○導線）` のような
コメントを読めてしまう。初見の人が読めるかは、書いた本人には判定できない。
このスキルは、足したコメントを**会話を知らない subagent** に読ませ、分からなかった所を元のセッションが直す。

見直しを AI レビュー（`/code-review`）と人のレビューの前に置くのは、直したあとのコメントを読ませるため。
`/simplify` の後に置くのは、`/simplify` がコードを書き換えるとコメントが実装とずれうるため。

## 基準

リポジトリにコメントの規約があればそれを優先する。無い部分は次のとおり。

- 残すのは、消すと次に触る人が間違った変更をしそうなコメントだけ
  - 採らなかった手と、仕様や設計にかかわる理由
  - コードから見えない前提のうち、崩れるとこのコードが誤動作するもの（別のリポジトリが送る値の形、データの事情）
  - 意図して揃えていない差
- 周辺環境の事情が理由の Why not（実行基盤や外部ツールの機能・制約で、ある実行方法を採らなかった理由）は、
  コメントに書かず PR 本文に書く。見分け方は「外の事情が変わったとき、このコードも直す必要があるか」。
  直す必要が無いものは、仕様が変わっていなくてもコメントだけを直し続けることになる
  - 直す前: `# ジョブ基盤の workflow 定義は引数を実行時に上書きできないので、定義にせず手で流す` /
    直した後: 手で流す手順だけを残す
  - ファイル冒頭のコメント（クラスやバッチの説明）には、実行方法の経緯が溜まりやすい
- 外を開かないと意味が取れない参照（issue / PR の番号、「仕様 9」のような節番号、チャットのリンク）で
  理由を済ませない。参照先に書いてある理由そのものを書く。経緯はコミットログと PR 本文に書く
  - 直す前: `# issue-12345（○○導線）` / 直した後: `# ○○導線の e2e が名前で引く店舗`
  - 参照先を残したいとき（外部の仕様書、upstream の不具合）は、理由を書いたうえで同じ行に URL を添える
- 書かないもの
  - コードの言い換え
  - 理由がコードそのものである文（「○○はレスポンスしないのでシリアライズしない」）
  - 今回の変更の経緯（「〜に変更した」「〜を追加」）

## 1. 足したコメントを抜き出す

```bash
~/.claude/skills/comment-check/scripts/added_comments.py > <一時ディレクトリ>/comments.json
```

既定ブランチとの merge-base から作業ツリーまでに足したコメントを、連続する行ごとのかたまり（`blocks`）で出す。
lint への指示（`rubocop:disable` など）は入らない。対象は Ruby・TS / JS・シェル・YAML などで、Markdown は見ない。

`count` が 0 なら、「足したコメントは無い」と伝えて終える（subagent は起動しない）。

## 2. subagent に初見で読ませる

Agent ツールで subagent を 1 つ起動する。**`subagent_type` は `general-purpose` にし、`fork` は使わない**
（fork は会話を引き継ぐので、初見にならない）。プロンプトには次だけを書く。issue の内容、変更の目的、
自分がコメントに込めた意図は書かない。

- リポジトリのパスと `comments.json` のパス
- かたまりごとに、そのファイルの前後のコードを読んでから判定すること
- **読んでよいのはリポジトリのコードだけ。** issue、PR、コミットログ、チャット、kb は開かない
  （開かずに読めるかを確かめるのが目的）
- 上の「基準」の全文
- 返す形: かたまりごとに `file:start-end`、判定（`残す` / `書き直す` / `消す`）、理由。
  `書き直す` には「初見の人がここで何を知りたくなるか」を問いの形で書く。書き直した文面は作らなくてよい
  （理由を知っているのは元のセッションなので）
- 同じ言い回しの問題が 2 か所以上にあれば、最後にその言い回しを挙げること（3 の候補にする）

## 3. 直す

subagent の判定を 1 件ずつ見て、元のセッションが直す。

- `書き直す`: 問いに答える内容をコメントに書く。答えが issue や仕様にしか無ければ、その要点を写す
- `消す`: 消す。経緯なら次の commit のメッセージに、周辺環境の事情なら PR 本文に回す（PR があれば本文の更新案をユーザーに見せる）
- 判定に同意できないときは残してよい。その理由を 5 の報告に書く
- コードは変えない。コメントと実装が食い違っているのを見つけたら、直さずにユーザーへ伝える
- subagent に読ませ直さない（PR ごとに 1 回）。直したあとは `/code-review` が読む

## 4. 機械チェックへの登録を提案する

今回見つかった問題のうち、**決まった言い回しで grep できるもの**は、AI に毎回読ませずに commit の前で止められる。
hook（`kb-checks.sh`）が `git commit` の前に kb の `checks/run` を呼び、足したコメントの行に
`checks/comments/patterns.tsv` の型が無いかを見ている。

1. kb を探す（`./kb` → `$HELLO_RUN_KB` → `~/git_clone/local/kb`）。`checks/comments/patterns.tsv` が無ければ、この節は飛ばす
2. 候補を選ぶ。条件は、既存の型に当たらないこと、正規表現で書けること、正しいコメントに当たりにくいこと。
   「残す価値が無い」のように読まないと判定できないものは候補にしない。無ければ何も聞かずに 5 へ進む
3. 候補ごとに、正規表現・今回当たった行・当たってはいけない近い例を見せて、足してよいかをユーザーに聞く。
   **承認なしに足さない。** commit を止める検査なので、誤検知が入ると全セッションの作業が止まる。
   聞けない実行（`claude -p` など）では、候補を報告に書くだけにする
4. 承認されたら、kb の `checks/README.md` の「コメントの型を足す」の手順で足す（fixture とテスト、全体での件数の計測まで）

人のレビューで受けた指摘を型にしたいと頼まれたときは、1〜3 を飛ばしてこの節だけを行う。

## 5. 報告する

- 足したコメントの数と、残した・書き直した・消した数
- 判定に同意せず残したものと、その理由
- 機械チェックに足した型、または見送った候補

## やらないこと

- 差分で足していない、既存のコメントの見直し
- コードの変更
- PR 本文・コミットログ・ドキュメントの推敲
