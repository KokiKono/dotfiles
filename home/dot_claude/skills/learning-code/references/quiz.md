# 出題と採点

判定前に `references/levels.md` のルーブリックを読むこと。

## 共通ルール

- **1 回のセッションで扱う topic は 3〜5 個まで。** それ以上は疲れて精度が落ちる
- 出題前に「今回測る項目」を箇条書きで提示し、合意を取ってから始める
- **答えを先に出さない。** 採点のときも、足りない観点だけを補う。
  正解の全文を貼ると「読んで分かった気になる」が残るだけで次回も答えられない
- 1 項目終わるごとに `scripts/skills-db.sh upsert` で保存する。
  まとめて最後に保存しない（途中で中断されたときに消える）

## A. 初期判定（未知の領域に初遭遇したとき）

**4 択 5 問。** `AskUserQuestion` で 1 問ずつ出す。

- 易 → 難の順。1 問目は「その言語/領域の最も基本的な意味論」、
  5 問目は「経験者なら踏んだことがある落とし穴」
- 選択肢は紛らわしくする。消去法で当たる問題は測定にならない
- 既知スタック（react/ts/laravel/mysql）との対比を問題文に入れてよい
- 5 問終わるまで正誤を言わない。最後にまとめて解説する

正答数から初期レベルを決める:

| 正答数 | 初期レベル |
|---|---|
| 0〜1 | `beginner` |
| 2〜3 | `junior` |
| 4 | `senior` |
| 5 | `professional` |

保存は領域を代表する 1 項目として:

```bash
scripts/skills-db.sh upsert <領域> "初期判定" <level> "4択5問 n/5 正答" "initial" <kind>
```

`kind` は `language` / `framework` / `domain` のいずれか。

## B. 記述式（PR 駆動・復習モード）

**3〜5 問、自由記述。** ユーザーの回答を読んでルーブリックに当てる。

問いは次の 3 系統から作る。1 topic につき 1 問、浅い回答が来たら同じ topic を 1 段深掘りする:

1. **何をしているか** —「この行が何をしているか、自分の言葉で」
   （junior 以上かの切り分け）
2. **なぜその書き方か** —「なぜ〇〇ではなくこの書き方なのか」「これを使わなかったらどうなるか」
   （senior かの切り分け）
3. **トレードオフ** —「この設計で困るのはどんなときか」「別案は何があって、なぜ採らなかったか」
   （professional かの切り分け）

深掘りは **1 topic あたり 1 回まで。** 答えられなければそのレベルで確定して次へ進む。

採点の出し方:

```
### ブロックと yield
判定: ジュニア — 何が呼ばれるかは説明できたが、Proc / lambda との return の違いに触れなかった
補足: ここで押さえると senior に届く観点は 〜
```

保存:

```bash
scripts/skills-db.sh upsert <領域> "<topic>" <level> "<判定の根拠を1行>" "PR #123"
```

## D. 解説ログを残す

出題セッションの最後に、**補足した解説を markdown で保存する。** 口頭で流すと COB で振り返れない。

```bash
dir="$(scripts/skills-db.sh logs-dir)"   # ~/.learning/input_logs
# ${dir}/YYYY_MM_DD_<summary>.md に書く
```

- ファイル名は `2026_10_05_jq-bash-pr24.md` の形。`<summary>` は**半角英数とハイフン**で、
  測った領域と出典が分かる短い語にする（同じ日に複数回やってもぶつからないように）
- **1 セッション 1 ファイル。** 既に同名があれば追記ではなく `<summary>` を変える
- 中身は topic ごとに次の形。**出題文と自分の回答も残す** — COB でどこで詰まったかを再現するため

```markdown
# 2026-10-05 jq / bash（PR #24）

## jq / as 束縛とパイプの評価順 — ビギナー

**問い:** （出した問題文）
**回答:** （ユーザーの回答。「わからない」ならそう書く）
**判定の根拠:** （upsert の note と同じ 1 行）

### 解説
（補足した内容）
```

保存したらパスをユーザーに伝える。

## C. topic の切り出し方（PR 駆動）

`gh pr diff` の差分から出題対象を選ぶ。全部は扱わない。

優先度の高い順:

1. **既知スタックに対応物が無い言語機能** — 自分の語彙で言い換えられないもの
2. **そのフレームワークの思想が出ている箇所** — 規約・DI・ライフサイクルに乗っている書き方
3. **ドメイン知識が無いと意図が読めない箇所** — 業務ルール、外部仕様、既存の経緯
4. **AI が勝手に足した非自明な実装** — エラーハンドリング、リトライ、キャッシュ、境界条件

除外するもの:

- 既知スタックの定型（React のフック、Eloquent、SQL）
- リネーム・フォーマット・import 整理のみの差分
- 設定ファイルの値替え（なぜその値かが論点なら 3 に含める）

topic 名は**検索できる粒度の名詞句**にする（`ブロックと yield`、`ActiveRecord のコールバック順序`）。
`Ruby の書き方` のような粗い名前は後で復習できないので避ける。
