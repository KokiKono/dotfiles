# issue の分析と WF の選び方

## 1. 分析の観点

order.md の「分析」に、次の 5 項目を 1〜2 行ずつ書く。

| 観点 | 見ること | WF への効き方 |
|---|---|---|
| 種類 | 新機能 / 既存の改修 / バグ修正 / リファクタ / 調査 / テスト追加 | 既存コードを触るなら maintenance 系 |
| 範囲 | 触る層（UI・API・DB・バッチ）、ファイル数の見込み、repo 数 | 狭ければ軽い WF、層が多ければ default 系 |
| 不確かさ | 原因・仕様・やり方のどれが分かっていないか | 原因不明なら実装の前に調査を挟む |
| 確かめ方 | 既存テストの有無、手元で動かす手段、UI の目視が要るか | テストが無い領域は write_tests のある WF |
| リスク | 課金・権限・データ移行・外部連携・公開 API | 高ければレビューの厚い WF、低ければ mini |

範囲は**実際にコードを grep して見積もる**。issue の文面だけで「小さい」と決めない。

## 2. 決める順番

### 2-1. playbook を引く

`playbook.md` に同じ型の項目があり、結果が良かったならその WF を使う。
結果が悪かった項目は、そこに書いた「次は」を採る。

### 2-2. builtin で足りるか

takt v0.71 時点の主な builtin。版が上がると変わるので、迷ったら
`$(scripts/takt.sh --root)/builtins/ja/workflow-categories.yaml` と各 YAML の `description` を見る。

| WF | 向く issue | 重さ |
|---|---|---|
| `maintenance` | 既存コードの改修・バグ修正。変更範囲外の契約を守り、因果のある差分に絞る | 重い（max 51） |
| `default` | 新機能・複数層にまたがる追加。シナリオ計画、テスト先行、並列レビュー、裁定つき修正 | 重い（max 51） |
| `simple` | 範囲の読める小〜中規模の変更。変更内容に応じて facet を自動で足す | 中（max 30） |
| `simple-mini` | 小さく明確な変更。テスト作成と最終確認を省く | 軽い（max 20） |
| `pure` | facet を足さずモデルの判断に任せる最小構成 | 中（max 30） |
| `research` / `deep-research` | 原因調査・仕様調査。コードは書かない | 軽い |
| `review` / `review-fix` | 既にある差分のレビュー / レビューして直す | 中 |

builtin で足りるのは、**差し込みたい知見が無く**、流れもそのままでよいとき。

### 2-3. 薄い WF で知見を差し込む（大半はここ）

builtin の `maintenance` / `default` / `*-mini` は、どれもコア（`development-core` か `mini-core`）を
`workflow_call` で呼び、引数で facet の一覧を渡しているだけ。同じ形の WF を書き、
引数の一覧に kb の knowledge を足す。書き方は `authoring.md` §薄い WF。

差し込む価値があるもの:

- 過去 issue で分かった、その領域の落とし穴（「この画面の状態は○○経由でしか変えない」など）
- repo 固有でエージェントが毎回間違える規約（CLAUDE.md に無いもの）
- この issue の前提になる調査結果（`research` を先に流した結果など）

差し込まないもの: CLAUDE.md / AGENTS.md の写し、issue 本文の写し（task.md に書く）、
一般論（builtin の facet が持っている）。

### 2-4. step から組む

流れ自体を変えたいときだけ。例:

- 原因が分からないバグ: readonly の調査 step → 調査結果を report に出す → 実装 → レビュー
- 実装は小さいがレビューを厚くしたい: 実装 1 step + parallel のレビュー
- テストの無い領域: 先に characterization test を書く step を置く

組み方は `authoring.md` §自分で組む。

## 3. 分けて発注するとき

- **原因不明のバグ**: まず `research` で調査だけ流し、結果を knowledge.md に落としてから実装 WF を発注する。
  1 本の WF に調査と実装を詰めるより、間で人が判断できる
- **複数 repo**: repo ごとに発注を分ける。API 側を先に流し、その差分を
  フロント側の knowledge.md に書いてから流す
- **大きい issue**: issue 内のタスクを独立した単位に割り、単位ごとに発注する。
  1 回の run が長いほど、途中の失敗で捨てる量が増える

## 4. takt に向かないもの

次は takt に流さず、その旨と理由をユーザーに返す。

- 1〜2 行の修正（WF を組む手間のほうが大きい）
- 仕様が決まっていない（先に issue で詰める）
- 本番データの確認や外部サービスの設定変更など、作業ツリーの外が主な作業
