# PR / Issue 本文のトーンパターン

自分が書いた PR 本文から抽出した構成・文体パターン。固有名詞・URL・数字は匿名化してある。

## 前提

**PR 本文は「レビュワーの時間を最小化する文書」として書く。** 何を変えたかの説明ではなく、
**どこを見ればいいか**と**なぜその判断にしたか**を渡すのが目的。文体は常体（〜する / 〜した）。

タイトルは Conventional Commits（`feat(scope): ...` / `fix(scope): ...` / `chore: ...` / `docs: ...`）。
日本語と英語のどちらもある。**スコープが1つのアプリに閉じる修正は日本語、共通ルール・AI 資産・
基盤寄りの変更は英語**の傾向。リポジトリの既存 PR に合わせる。

## 構成

バグ修正:

```
## 概要        何を直すか。1〜2行
## 原因        なぜ起きていたか。仕組みのレベルまで降りる
### 計測       実測値の表。再現しなかった環境も書く
## 変更内容    番号リスト。1項目ごとに「何を」+「なぜそうしたか」
## 確認方法    実際に叩いたコマンドと、出力の抜粋
## レビュー時の注意点
```

機能追加:

```
## 概要                 何をするか。設計判断の前提も1段落で書く
## レビュワー確認ポイント  判断コストが高い順に並べる（後述）
<details>変更内容・テスト計画・チェックリスト</details>
```

大きめの調査系:

```
# Context               何が起きているか。切り分けの経緯
## 計測結果              表 + ログの生抜粋。当初の仮説が否定されたことも書く
# Changes in the codebase
## 対策                  なぜこの対策で直るか
# Additional information  環境構築手順・読み方・注意点
# Test plan               checkbox。済みは [x]、実機確認待ちは [ ]
```

## 文体の特徴

### 1. 「レビュワー確認ポイント」を判断コストが高い順に並べる

これが最大の特徴。全部を平等に見せず、重い順に並べて**軽いものは流していいと明言する**。

```
## レビュワー確認ポイント

判断コストが高い順に 4 点あります。

**1. ○○を持つことの是非と、安全装置の設計**

これが一番重く、ここだけ見ていただければ他は流して構いません。
誤動作すると△△が止まるか、□□に入れなくなります。入れた装置は次のとおりです。

- （箇条書き）

判断の分かれ目は上限の ○ 件と、確認を挟む範囲です。範囲は（規約へのリンク）に明文化しました。
```

- 各ポイントは太字の見出し + 3〜6行
- 「判断の分かれ目は〜です」で、レビュワーに考えてほしい論点を1文に絞って渡す

### 2. 該当行へのリンクを本文に埋める

「〜ようにしています」の主張には、必ず GitHub の行範囲リンク（`#L226-L240`）を付ける。
コードを探させない。

### 3. 仮説が否定された過程を残す

調べて分かったことだけでなく、**当初疑っていたことが違ったこと**を書く。
これがあると同じ調査を繰り返さずに済む。

- 「当初疑っていた「1問目だけ先頭が欠ける」は否定され、○○の遅延指定では直らないことが分かった。」
- 「staging とローカルで再現しなかったのは、このコンポーネントが △△ でガードされており、
   そもそも描画されていなかったためです。」

### 4. 計測値とログを生で貼る

表とコードブロックの生ログを並べる。「速くなった」で終わらせない。

```
17:07:43.519  routeChange(routeConfigurationChange)   inCh 1→4   ← マイクが開く
17:07:43.599  heldPlaybackStartup {"playbackIndex":1,...}
17:07:44.135  routeChange(routeConfigurationChange)   ┐ 再生開始の 536ms 後
```

矢印コメント（`← 〜`）と罫線（`┐│┘`）で、ログのどこを見るかを指す。

### 5. 「なぜ他の案にしなかったか」を1文で書く

実装の選択肢を潰した理由を、その場に短く置く。

- 「補うと台帳に無い権限が実態に生まれ、次の差分でそれが削除候補になり、削除すると□□が
   見えなくなる往復が終わりません。エラーで止めて台帳を直してもらう形にしました。」
- 「割り込ませると切替が実音声の途中に戻るため」
- 「絞らないと、タップでも「乗った」扱いになって開いた直後に閉じてしまう。」

### 6. UI 変更は見た目の根拠を書く

デザイン変更では「原本ではこうなっている」「参考サイトはこれ」まで書く。好みの話にしない。

### 7. 詳細は `<details>` に畳む

変更ファイル一覧・テスト計画・チェックリストは畳んで、本文はレビュー判断に必要なものだけにする。

### 8. Test plan は状態が分かる checkbox

`[x]` は自分で確認済み、`[ ]` はレビュワー or 実機での確認待ち。「確認予定」を曖昧にしない。

## やらないこと

- 差分の要約だけ（何を変えたかは diff を見れば分かる。なぜ・どこを見るかを書く）
- 「動作確認しました」だけ（何をどう叩いて、何が出たかを書く）
- 全部の変更点を平等に並べる（重い順に並べて、軽いものは流していいと言う）
- 数字なしの性能主張
- レビュワーにコードを探させる（行範囲リンクを貼る）
