# 社内文書のトーンパターン

Notion に書いた技術設計・タスクチケット・運用マニュアル・長文エントリーから抽出した文体パターン。
固有名詞・URL・数字は匿名化してある。

## Slack との最大の違い

**文書では「！」と絵文字を使わない。常体（〜する / 〜だ）で書き、判断を言い切る。**
Slack の低姿勢な丁寧語をそのまま持ち込むと別人の文書になる。ここは切り替える。

一人称は「私」。社外公開する文章では「僕」（note の過去記事に合わせる）。

## 文体の特徴

### 1. 太字で「要するに」を刺す

セクションの冒頭または途中に、その節の結論を1文の太字で置く。読者が太字だけ拾って骨子が分かるようにする。
乱用しない（1セクションに1〜2箇所）。

- 「**目的は○○の導入で、△△はその前提条件。**」
- 「**現状の配信に問題が出ているから入れるわけではない。**」
- 「**作り直しが要る。**」
- 「**この5年8ヶ月で意味あるものを作るエンジニアの土台を作れたのは、本当に幸運だった**」

### 2. 「やらない理由」「入れない理由」を必ず書く

採用しなかった選択肢と、その理由をセットで書く。読者の「なぜこっちじゃないの？」を先に潰す。

- 「グループを使わない理由は、**API が「継承」と「直接」を区別できない**ことです。」
- 「月額固定のプランは従量課金より安いが、○○の目安を通常月で △%、繁忙月で △% 超えるため見送る。
   実績が見えてから切り替えることは可能。」
- 「移管すると○○の宛先や各種の認証用レコードの影響範囲を洗い出すところからになる」

### 3. 数字を必ず入れる

「重い」「遅い」で終わらせない。転送量・所要時間・件数・金額を実測値で書き、表にする。
比較対象も並べる（現行 vs 変更後、A案 vs B案）。

- 「1ページあたりの転送量が ○ メガバイトあり、△（○ メガバイト）の2倍以上重い」
- 「本番 / CPU 6倍: FCP 732ms、220ms 表示 → 1551ms `opacity:0` → 2703ms 復帰（**1152ms 白**）」

### 4. 専門用語を日本語に開く

読者に非エンジニアが混ざる文書では、カタカナ語・英語をあえて日本語にする。

「レンタルサーバー」「名前解決」「保持時間」「素材」「配信」「閲覧者のホスト名」
「キャッシュ破棄」「実行者自身」——などのように、その文書の読者が知っている語まで降りる。

### 5. 「今回は着手しないもの」の節を置く

スコープの外側を明示的に列挙する。checkbox で残し、なぜ今やらないかを1行添える。

```
## 今回は着手しないもの
- [ ] ○○の圧縮と変換。転送量が費用の8割以上を占めており、6割減らせれば月△円まで下がるが、
      本件の導入には不要
- [ ] △△の分離。共通になっているため数値に○○の分が混ざる
```

### 6. 前提が変わったら差分表を書く

以前の資料・以前の方針と現状がずれたとき、「資料の記述 / 現状」の2列表で並べる。書き直さずに差分を残す。

### 7. 責任境界を言い切る

運用ルールの文書では、誰が何を持つかを曖昧にしない。受動態で主語をぼかさない。

- 「○○は、原則として実装者または依頼元チームの責任です」
- 「△△は技術的なリスク確認であり、デザイン修正・文言調整・仕様調整の代行ではありません」
- 「リリース依頼は公開作業の依頼であり、追加実装・デザイン修正・仕様変更は暗に含みません」
- 「追加修正が必要な場合は、リリース作業に含めず、別タスクとして起票し優先度調整を行ってください」

期待値がずれやすい論点は、本文と別に callout / チェックリストで二重に置く。

### 8. FAQ で反論を先に潰す

想定される質問を読者の言葉（口語）で書き、答えは条件付きで言い切る。

- 「Q: ○○を公開するのにどれくらい時間がかかりますか？
   A: 上記手順の場合は△△が終わり次第公開出来ます。その他のケースではケースバイケースなので都度ご相談してください。」
- 「Q: ○○をベースにブラッシュアップ依頼をしてもいいですか？
   A: 依頼して構いません。チケットにその旨を記載してください。」

「可能です。ただし〜」「構いません。ただし〜」の形が多い。許可して条件を付ける。

### 9. 長文では具体的なエピソードと数字で語る

主張を先に置かず、実際の出来事 → そこから分かったこと、の順で書く。抽象論・美文で埋めない。

- 「GitHub のログを遡ると、私の最初の PR は ○年○月○日でした。表から「所要時間」という列をひとつ消すだけの、小さな変更です。」
- 「一番覚えているのは本番のマイグレーションが動かず、コンテナに入って調べたら、本番用の env ファイルを
   用意し忘れていただけ、ということです。」
- 自分の失敗を隠さない。落として笑いにする（「いま読み返すと笑ってしまうようなミス」）
- 締めで一段だけ温度を上げる。「本当にありがとうございました！」のように、最後だけ「！」を許す

## 文書の構成テンプレート

### 技術設計・タスクチケット

```
## 概要        何をするか。1〜2段落。保留していた経緯があれば書く。関連資料をリンクで並べる
## 目的        なぜやるか。太字で本質を刺す。「〜だから入れるわけではない」も書く
## 構成の要点  表（項目 / 内容）
## 費用        表。現行との比較と、判断の言い換え（「安くする施策ではなく○○を維持するための費用」）
## 決定事項    箇条書き。決めたことと、その理由を同じ行に入れる
## 進め方      サブチケットの分割
## 今回は着手しないもの
```

### 運用マニュアル

`目的` → `前提・要件` → `用語定義` → `実施手順とポイント`（フェーズごとに番号リスト）→
`責任範囲` → `依頼前チェックリスト` → `FAQ` → `関連資料` → `変更履歴`

※これは社内のマニュアルテンプレートに沿った構成。テンプレートがある文書ではその見出しを崩さず、
中身の書き方（上の1〜8）だけを著者の文体に寄せる。

## やらないこと

- 官僚的な言い回し（「〜に鑑み」「〜に資する」「〜を推進していく所存」）
- 中身のないバズワード。抽象的な効能だけ並べる
- 数字なしの「重い」「速くなる」「改善される」
- 受動態で主語をぼかす（誰がやるか、誰の責任かを必ず書く）
- スコープを曖昧にしたまま進める（やらないことを書かない）
- 文書に「！」と絵文字を持ち込む（締めの1文だけは例外）
