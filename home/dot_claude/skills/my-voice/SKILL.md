# my-voice

著者の口調・トーンで文章を書くスキル。

口調のリファレンスは**必ず読んでから書く**こと。場面ごとに参照先が違う:

| 場面 | リファレンス |
|---|---|
| Slack（チームチャンネル・スレッド返信・DM） | `references/slack-voice.md` |
| 社内文書（Notion の設計・チケット・マニュアル・長文エントリー） | `references/formal-voice.md` |
| PR / Issue 本文 | `references/pr-voice.md` |

## 3系統は別物として扱う

著者は媒体でトーンを切り替える。**同じ丁寧語を全部に流用すると別人の文章になる。**

1. **Slack** — です/ます調 + 「！」+ 文末の絵文字。低姿勢で、依頼は疑問形。短い
2. **社内文書** — 常体（〜する / 〜だ）。「！」と絵文字は使わない。判断を言い切り、数字と表で示す
3. **PR / Issue** — 常体。レビュワーの時間を最小化する構成（重い論点から並べる）

## 使い方

### Step 1: 文脈を判断し、足りない情報を聞く

まず以下を把握する。明示されていない項目は**推測せずに確認する**:

- **どの媒体か** — Slack / Notion / GitHub。ここでトーンが決まる
- **誰に向けて書くか** — チームメンバー、他部署、非エンジニア、全社、外部
- **何を伝えたいか** — 報告、依頼、相談、提案、アナウンス、返信

確認の深さは媒体で変える:

| 媒体 | 確認の方針 |
|---|---|
| **Slack** | 宛先・目的が曖昧なら確認する。内容はユーザーの指示から書ける場合が多い |
| **PR / Issue** | 差分とコードを読めば大半は書ける。ただし**判断の理由**と**レビュワーに見てほしい論点**は本人しか知らないので聞く |
| **社内文書** | **必ず確認する。** 頭の中にある前提がないと空虚な文書になる。ただし質問は **3〜5個に絞る** |

社内文書で優先的に確認すべき項目（この中から3〜5個選ぶ）:

- なぜやるのか（目的。手段が目的化しているならそれも書く）
- 採用しなかった選択肢と、その理由
- 数字（現状の実測値、費用、件数、期間）
- スコープの外側 —「今回は着手しないもの」に何を置くか
- 誰が何の責任を持つか（運用ルールの文書なら必須）
- 想定される反論・質問（FAQ に置くもの）

### Step 2: 書く

リファレンスの実例を参考に、著者の口調で書く。読み上げて不自然なら口癖を削る。

### Step 3: 出す

Slack はそのまま貼れる形で出す。**リンクは `<url|text>` にせず生 URL を行末に置く**
（入力欄に貼ると壊れる）。

## 注意事項

- **模倣しすぎない。** 不自然なほど口癖を詰め込まない。自然に読めることが最優先。
  とくに「！」と絵文字は、実データでも1メッセージに絵文字1つが基本
- **内容の判断は本人のもの。** 口調は再現できるが、事実関係・意思決定は確認する。
  分からないことを埋めて書かない
- **初稿は最小形で出す。** Slack は要件だけ書いて出し、背景・理由・具体例は本人が求めたときに足す。
  長い初稿を削るより、短い初稿に足すほうが往復が少ない
- **調べた量と書く量を連動させない。** 資料や差分を読み込むほど盛り込みたくなるが、
  相手の判断を左右しない詳細（Issue 番号、調査の経緯、個別の未実装項目）は落とす
- 「自分っぽくして」と言われた場合は、**内容を変えずにトーンだけ調整する**
- 社内文書のテンプレート（`目的` / `前提・要件` / `用語定義` / `FAQ` / `変更履歴` 等）がある場合は
  **見出しを崩さない。** 文体だけ著者に寄せる

## リファレンスの更新

リファレンスは実データ（Slack・Notion・GitHub）からの抽出物。出した下書きに違和感があったら、
その場で直すだけで終わらせず**該当リファレンスに1行追記する**こと。使いながら育てるファイル。

このスキルは chezmoi 管理下（`home/dot_claude/skills/my-voice/`）にあり、リポジトリは **public**。
実例を追記するときは**固有名詞・URL・具体的な数字を `○○` / `△△` / `（リンク）` に匿名化する**。
