# 動作確認ページの形

ページは「後で戻ってきた自分が、ここだけ見て続きを始められる」ことを目指す。
チェックボックスは Notion の to-do ブロック（`- [ ]`）で書く。

## タイトルとプロパティ

- タイトル: `#<issue 番号> <issue タイトル> 動作確認`
- 起票先がデータベースなら、行に次のプロパティを入れる（§2 の再開判定はこの 2 つで引く）

  | プロパティ | 入れるもの |
  |---|---|
  | `種別` | `動作確認` |
  | `Github Issue` | issue の URL |
  | `date:登録日:start` | 今日の日付 |

  `種別` を空にすると、同じ DB の他のスキルの行と見分けられなくなる。
  ユビキタス言語用の列（`ひとこと定義` など）は空のままにする
- 起票先がページなら、issue の URL を本文の先頭に書く

## 本文

```markdown
- issue: <URL>
- PR: <URL または「なし」>
- 環境: <ローカル / QA / staging / 本番>
- 追加要望: <引数で受けた要望。無ければ省く>

## 環境
<再開に要る情報だけ>
- worktree: <パス>（ブランチ <branch>）
- フロント: <アプリ名> http://localhost:<port>（dev-server の pane <id>）
- BE: <compose のプロジェクト名 / ポート>
- テストデータ: <作ったデータの ID・名前、または QA で使う店舗名>

## 準備
- [ ] <まだ済んでいない準備。済んだものはチェック済みで書く>

## 確認
### 1. <ケース名>
- [ ] <操作> → <期待する見え方>
- [ ] <…>

所感:

### 2. <ケース名>
…

## 後片付け
- [ ] <作ったデータを消す / 戻す。ローカルだけなら「不要」と書く>

## 全体の所感
<確認し終えてからユーザーが書く欄。空のまま置く>

<details>
<summary>選ばなかった確認</summary>

- <単体テストで十分なもの>（<テスト名 または「テスト未作成」>）
</details>
```

- 「所感:」はケースごとに空の段落で置く。確認しながら「思ったより遅い」「文言が分かりにくい」
  のような手触りを書くための欄なので、こちらで埋めない
- ケースが無いと判断した場合も起票はせず、§4 の根拠を会話で返して終える
- 再開時に書き換えてよいのは「環境」節と「準備」節だけ。チェック状態と所感はユーザーのものなので触らない
