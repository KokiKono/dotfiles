# hello-manual-test

issue を手で確かめるときに、**何をどの環境でどの順に見るか**を決めて Notion に残す。
ユーザーは複数の作業を並行していて、動作確認は途中で止まりやすい。
だから成果物は Notion のページにする。チェックの進み具合と環境の情報をそこに残しておけば、
後で戻ってきたときにページだけ見て続きから再開できる。

**引数のうち issue / PR の URL 以外は、動作確認への追加要望として扱う**
（「スマホ幅でも見たい」「予約の取消だけでいい」など）。手順の中で既定の判断とぶつかったら、
要望のほうを採る。ただし下の「守ること」に反する要望なら、従わずに理由を伝える。

ページの形は `references/notion-page.md` にある。起票する前に読む。

## 0. 設定を読む

```bash
cat ~/.claude/hello-manual-test.local.json
```

| キー | 意味 |
|---|---|
| `notion_parent_url` | 起票先。ページなら子ページを、データベースなら行を作る |
| `notion_data_source_url` | 起票先がデータベースのときの `collection://…`（ページなら空） |
| `test_stores` | staging / QA / 本番で触ってよい店舗名の配列。**これ以外の店舗は触らない** |
| `environments` | 環境ごとの URL やログイン方法のメモ（`local` / `qa` / `staging` / `production`） |
| `github_owner` | issue を検索するときの org |
| `dry_run` | `true` なら Notion に書かず、書く内容を表示するだけ |

**このファイルは追跡外**（スキル本体は public リポジトリにある）。店舗名・環境の URL は
ここにしか書かない。ファイルが無い / `notion_parent_url` が空なら `setup` モードへ。
引数が `setup` のときも同じ。

## 1. 前提

手順を組む前に、次の 2 つを頭に置く。どちらも、ここを外すと実害が出る。

- **staging・QA・本番は同じ DB を使っている。** QA で作った予約も消した設定も、本番の店舗と
  利用者にそのまま見える。だからローカル以外では `test_stores` の店舗しか触らず、
  作ったデータは手順の最後で元に戻す
- **ローカルでは同じアプリが複数のバージョンで同時に動いている**（worktree ごとに dev サーバーがある）。
  `localhost:3000` を開いても、それが今の issue のブランチとは限らない。
  ポートは必ず `dev-server list --json` で、この worktree のものを確かめてから使う

## 2. 中断した続きか確かめる

起票先に同じ issue のページがあるか探す。データベースなら `notion-query-data-sources` で
`種別 = '動作確認'` かつ issue の URL で引き、ページなら `notion-search` で issue 番号を引く。

起票先は hello-search や ubiquitous-language と同じ個人メモ DB で、同じ issue の
イシュー検討メモも入っている。**issue の URL だけで引くと、それを動作確認のページと
取り違えて再開してしまう**ので、`種別` で必ず絞る。

- **あれば新しく作らない。** ページを読み、チェック済みの項目と「環境」節を確かめて、
  未チェックの項目から再開する。環境の情報が古くなっていたら（サーバーが止まっている、
  ポートが変わった）§5 だけやり直して「環境」節を書き換える
- 無ければ §3 へ

## 3. 環境を決める

issue と PR の状態を確かめる。

```bash
gh issue view <url> --comments
gh pr list --search "<issue の URL か番号>" --state all --json number,url,state,headRefName,mergedAt
```

| 状態 | 環境 |
|---|---|
| PR がまだ無い | ローカル |
| PR が open | ローカル（QA に出ていればそれも可。`environments.qa` を見る） |
| PR がマージ済み | staging。本番へ出たあとの確認なら本番 |

ユーザーが環境を指定したらそれに従う。判断がつかなければ 1 問だけ聞く。
本番で確かめるケースは、読み取りで済むもの（表示・遷移）に絞る。データを作る確認は
QA / staging で済ませる。

## 4. 確認ケースを選ぶ

issue の本文・コメント・リンク先の仕様（Notion があれば読む）と、PR の差分
（PR が無ければ `git diff origin/<default>...`）を読み、**画面を触らないと分からないこと**だけを選ぶ。

選ぶもの:
- 画面に出る内容・文言・並び順・状態ごとの出し分け（空・読み込み中・失敗を含む）
- 操作の流れ（遷移、戻る、二度押し、途中離脱からの再開）
- 他の画面や他の役割（店舗側 / 利用者側）への波及
- 幅（スマホ / PC）で崩れやすい箇所

外すもの:
- 入力値のバリデーションや計算ロジックのように、単体テストで確かめきれるもの。
  テストがあるならそのテスト名を、無いなら「単体テストで見るべき」と 1 行で添えて外す

**選ぶものが無ければ、無いと答える。** 例えば内部のリファクタリングで画面に差分が出ないなら、
差分のどこを見てそう判断したかを示して終える。無理にケースを作ると、確認が儀式になる。

各ケースは「操作 → 期待する見え方」の 1 行で書けるまで具体にする。
確認の順序は、データの準備が少ないもの・前提になるものから並べる。

## 5. 環境を用意する

### ローカル

- **フロントの dev サーバーは dev-server スキルに任せる**（`dev-server --json <app>`）。
  同じ worktree で既に動いていれば CLI が再利用する。`conflict` が返ったら起動せずユーザーに渡す
- **BE は Docker。** worktree のリポジトリの README / `compose.yml` から起動方法を読む。
  起動前に `docker compose ps` でこの worktree のコンテナが動いていないか確かめ、動いていれば使い回す。
  別の worktree のコンテナが同じポートを握っていたら止めずにユーザーに聞く（向こうの作業を壊すため）
- テストデータはローカルの DB に作ってよい。seed や rails runner など、リポジトリにある手段を使う。
  作ったデータの見つけ方（ID・名前）をページに残す

### QA / staging / 本番

- データは作らず、**作る手順を提示する**。どの `test_stores` の店舗で、どの画面から何を入れるか
- 後片付けの手順も対で書く（作った予約の取消、変えた設定を戻す）。DB が本番と共通なので、
  残ったデータは本番の画面に出続ける
- 利用者に通知が飛ぶ操作（メール・SMS・プッシュ）は、宛先が自分であることを確かめる手順を先に置く

用意できなかったもの（認証情報が要る、ユーザーの手が要る）は、ページの「準備」節に
未チェックの項目として残す。

## 6. Notion に起票する

`references/notion-page.md` の形で書く。`dry_run` が `true` なら内容を表示して終える。
起票したら 1 行で報告する。

```
🧪 「#123 ○○ 動作確認」を起票（リンク）— ケース 6 件、環境: ローカル
```

## setup モード

1. 起票先の Notion ページかデータベースの URL を聞く。データベースなら fetch して
   `collection://…` を取り、`種別` 列に `動作確認` の選択肢があるか、issue の URL を入れる列が
   あるか確かめる。無ければ足してよいか聞く
2. `test_stores` を聞く（staging / QA / 本番で触ってよい店舗の名前）
3. 環境の URL は聞けた分だけ `environments` に入れる。空でもよい
4. `github_owner` は `~/.pzshrc` の `HELLO_RUN_ISSUE_REPO` から取れる:
   `zsh -c 'source ~/.pzshrc; print ${HELLO_RUN_ISSUE_REPO%%/*}'`
5. `~/.claude/hello-manual-test.local.json` に書く。`dry_run` は最初 `true` にする

## 守ること

- **`test_stores` 以外の店舗を、ローカル以外の環境で触る手順を書かない。** ユーザーに頼まれてもしない
- **本番でデータを作る・変える手順を書かない。** 必要なら QA / staging で同じことを確かめる
- **他の worktree の dev サーバーやコンテナを止めない。**
- **社内の固有名詞をこのスキルのファイルに書かない。** 店舗名・org・URL は local.json 側に置く。
  `references/` も含めて public リポジトリに入っている
